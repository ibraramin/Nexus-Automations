# Deployment

Only what the repository configuration actually does is described here.

## Build: a static export

`next.config.ts` sets:

```ts
const nextConfig: NextConfig = {
  output: "export",
};
```

Its comment describes the target as a fully static site with no SSR or route
handlers, and notes that `next build` emits plain HTML into `out/`. Running:

```bash
npm run build      # next build
```

writes the static site into `out/`. The README records the observed result of
this command as **15/15 static pages generated** into `out/`. There are no
`app/api` routes and no server runtime in this repo; adding either would change
the deployment model.

## Publish: Cloudflare Workers assets

`wrangler.jsonc` contains:

```jsonc
{
  "name": "automation-portfolio",
  "compatibility_date": "2026-08-10",
  "assets": {
    "directory": "./out",
    "not_found_handling": "404-page"
  }
}
```

So `wrangler` serves the `out/` directory as static assets from a Worker named
`automation-portfolio`, using the `404-page` fallback for not-found requests.
No other Workers configuration, binding or route is declared in that file.

`package.json` defines:

```json
"deploy": "npm run build && wrangler deploy"
```

Therefore:

```bash
npm run deploy
```

first rebuilds the static export and then runs `wrangler deploy` against the
asset directory above. There is no separate build step to configure: `out/` is
always regenerated by the `npm run build` half of the command.

## Why `npm run start` is not usable

`package.json` also defines `"start": "next start"`, but `next start` expects a
Next.js server to run. With `output: "export"` there is no server — only static
files — so the README states that `npm run start` is not usable with this
export. It is a leftover standard script, not a deployment path.

## Preview locally

Preview the generated files with any static file server. The README's example
is:

```bash
npm run build
npx serve out
```

There is no need for `NEXUS_MOCK` to preview the site: the demos either use
checked-in sample data or run tesseract.js in the browser. `NEXUS_MOCK=1` is only
required by the offline demo script, as described in [Usage](USAGE.md).

## Node version and CI parity

`package.json` declares:

```json
"engines": { "node": ">=26.0.0" }
```

CI (`/.github/workflows/ci.yml`) has one `verify` job on `ubuntu-latest` that:

1. checks out with `actions/checkout@v4`;
2. sets up Node with `actions/setup-node@v4`, `node-version: "26"` and
   `cache: npm` — the workflow comment explains that Node 26 gives
   `node --test` native TypeScript type stripping and a stable `node:sqlite`,
   so the offline tests need no extra runner or dependencies;
3. runs `npm ci`, `npm test`, `npm run build`;
4. runs `npm run demo` with `NEXUS_MOCK: "1"`.

The workflow triggers on pushes to `main` and on pull requests. The README
records that the local verification runtime was Node 26.11.1, so local and CI
runtimes match at the major-version level. Use Node 26 or newer locally to keep
the same test behaviour (type stripping and `node:sqlite`) as CI.

## What is not configured here

To avoid overstating the setup, the following are not present in the read
configs and are therefore not described by this document: custom domains or
DNS, Wrangler secrets or environment bindings, a `wrangler.toml`, a Next.js
server or `app/api` handlers, and any deploy command other than
`npm run deploy`. Environment variable *names* (including reserved, unused
provider names) are listed in [Usage](USAGE.md#environment-variable-names) and
in `.env.example`; no values are committed.
